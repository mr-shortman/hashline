# Metrics

Targets, where we stand, and how it is measured. Targets only ever get
stricter; a miss leads to profiling, never to a quietly raised number.

**Status: 2026-09-11.** Development machine (Ubuntu 26.04, GTK 4.22.4,
Wayland/GNOME, discrete GPU), release build, `GSK_RENDERER=cairo`. None of this
is acceptance: that needs n >= 30 on the reference machine with integrated
graphics, which is not chosen yet.

OK = met, MISS = missed, TODO = not measured yet. v1 closed with the misses
it has; they are listed once in [limitations.md](limitations.md) instead of
being carried as tasks. These numbers are the baseline v2 must not regress
against.

## Startup and opening

"Readable" means the first frame that shows document text, proven by OCR on a
screen capture. An empty window does not count.

| Metric | Target (p95) | Current (p95) | |
| --- | ---: | ---: | --- |
| Start to readable text, 100 KiB | <= 120 ms | 172.0 ms | MISS |
| Start to readable text, 1 MiB | <= 150 ms | 139.2 ms | OK |
| Start to readable text, 10 MiB | <= 300 ms | 205.9 ms | OK |
| Open in running instance, 100 KiB | <= 40 ms | - | TODO |
| Open in running instance, 1 MiB | <= 80 ms | - | TODO |
| Open in running instance, 10 MiB | <= 250 ms | - | TODO |

Startup numbers are n = 30 in a `nested-headless` session with the settings
portal already running, as a real session has it. Where 100 KiB loses its time:
the document is ready before the first tick of the frame clock, so the first
frame pays ~28 ms of font warm-up in one go. Parsing (0.7 ms) and first-screen
layout (0.3 ms) are not the problem.

## Fixtures

Deterministic, generated by `benchmarks/generate.rs` and verified byte for byte
against the SHA-256 manifest `benchmarks/fixtures/metadata.json`.

| Fixture | Content |
| --- | --- |
| `small`, `medium`, `large` | ~100 KiB, 1 MiB, 10 MiB of README-like Markdown |
| `long-line` | one paragraph of a million characters without spaces |
| `large-code` | one fenced code block, 70,000 lines |
| `wide-table`, `deep-list`, `many-blocks` | layout stress cases |
| image fixtures | many images, large images |

```sh
python3 benchmarks/fixtures.py           # generate and verify
python3 benchmarks/fixtures.py --check   # verify only
```

## How to measure

```sh
# Quick regression check after a change (n = 5, small only, never acceptance)
python3 benchmarks/run.py bench --quick

# The competitive targets, about an hour
python3 benchmarks/run.py compare --only content,memory --fixtures small,medium,large \
    --viewers hashline,viewmd,mdview,md-viewer --renderers cairo \
    --repetitions content=30,memory=8 --session nested-headless

# Show the matrix and the estimated duration without starting anything
python3 benchmarks/run.py compare --only content,memory --plan
```

Groups: `stages`, `startup`, `content`, `memory`, `idle`, `scroll`,
`interaction`, `tabs`, `reload`, `stability`. `compare` runs the subset that can
be measured from outside, over Wayland, `/proc` and the compositor, and works
the same for every viewer; `bench` adds the instrumented groups that only
Hashline has. Both call the same implementation per group, so there is no
second measurement path that could drift.

**Rules that keep the numbers honest**

1. Content proof is mandatory: the time to the first frame *containing document
   text*, never to a window.
2. Interleave viewers and repetitions, and discard the warm-up run; a cold GPU
   driver added 52 MiB to the first memory sample of a session.
3. Record renderer and backend per viewer.
4. A viewer that cannot show a fixture is reported as "no result", never
   dropped from the table.
5. Memory is measured with a private D-Bus started *next to* the application,
   so portals, gvfs and dconf never land in the measured process group. The
   settings portal is started before timed launches.
6. Frame timing comes from Mutter's presentation marks for the monitor, which
   include every client, so it is a lower bound on our own quality, not an
   acceptance of it.
7. Anything with n < 30 is marked `sufficient: false` and is not acceptance.
